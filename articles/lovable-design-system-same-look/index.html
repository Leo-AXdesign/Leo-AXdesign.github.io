읽을거리 · AI 디자인

러버블은 왜 '디자인 방향 3안'을 없앴을까, 비슷비슷한 AI 화면과 디자인 시스템

러버블이 첫 빌드 전의 디자인 방향 세 가지 선택 단계를 없앴고, 디자인 시스템은 모든 유료 플랜에서 쓸 수 있다. 공식 변경 기록과 문서로 무엇이 확인되고 무엇이 비어 있는지, 내 규칙을 한 번 정해 두는 법을 정리했다.

2026년 10월 19일 · 읽는 데 약 7분

이 글의 차례

  1. 무엇이 바뀌었나
  2. 디자인 시스템은 어떻게 생겼나
  3. 쓰기 전에 알아 둘 한계
  4. 같은 시기의 다른 변화

  6. 디자이너에게 이것이 의미하는 것
  7. 그래서 지금은
  8. 정리하면

러버블이나 커서로 화면을 몇 개 만들다 보면 이상하게 다 비슷해 보인다. 둥근 카드, 비슷한 보라색, 비슷한 여백. 프롬프트를 바꿔 다시 시켜도 결이 같다. 그래서 "디자인 감이 없어서 그런가" 하고 넘기기 쉽다.

러버블의 공식 변경 기록(changelog)에는 이 문제와 관련된 항목이 최근 몇 주 사이에 몇 개 올라왔다. 하나는 첫 빌드 전에 보여 주던 '디자인 방향 3안' 단계를 없앴다는 것이고, 다른 하나는 디자인 시스템이 모든 유료 플랜으로 열렸다는 것이다. 이 글은 러버블 변경 기록과 공식 문서를 직접 열어 확인한 내용만 옮기고, 확인되지 않은 부분은 따로 적는다.

러버블의 공식 변경 기록과 문서(8~10월 항목)를 바탕으로 썼다. '디자인 시스템을 쓰면 화면이 덜 비슷해진다'는 건 공개된 비교 자료가 없어서, 그 부분은 내 해석이다. 플랜 설명은 검색 요약과 공식 문서가 서로 달라 뒤에서 따로 적었다.

무엇이 바뀌었나

공식 변경 기록에서 이번 글과 관련된 항목을 모으면 이렇다.

날짜항목내용
2026-08-19디자인 시스템모든 유료 플랜에서 사용 가능. 연결하면 모든 빌드가 컴포넌트, 토큰, 디자인 규칙을 물려받는다

2026-10-08첫 빌드 전 디자인 방향 제거시각적으로 열려 있는 프롬프트에서 보여 주던 3가지 방향이 사라졌다
2026-10-12파일 탭 이미지 편집이미지 위에 직접 표시해 고칠 수 있고, 결과는 새 파일로 저장된다

출처: Lovable 변경 기록

디자인 방향 3안이 사라졌다

변경 기록 문장을 옮기면 "The three design directions Lovable showed before building a visually open-ended prompt have been removed."이다. 말하자면 "예쁘게 만들어 줘"처럼 모양을 정하지 않은 프롬프트를 던지면, 예전에는 첫 빌드 전에 방향 세 가지를 보여 줬다. 이제는 그 단계 없이 입력한 설명을 바탕으로 바로 모양을 만든다.

다만 색, 글자, 레이아웃을 프롬프트에서 정하지 않았다면 이 세 가지는 여전히 물어본다고 변경 기록이 밝혔다. 예전 대화는 그때 고른 방향을 그대로 유지하지만 미리보기는 보이지 않는다.

왜 뺐는지 이유는 변경 기록에 적혀 있지 않다. 그래서 "방향 선택이 소용없어서 뺐다"고 읽으면 안 된다. 확인되는 것은 '단계가 없어졌다'는 사실까지다.

디자인 시스템은 유료 전 플랜으로

8월 19일 항목은 "Create a design system and attach it to your projects so every build inherits your components, tokens, and design rules."라고 적었다. 풀어 쓰면, 버튼·카드 같은 부품과 색·글자 크기 규칙을 한 번 만들어 프로젝트에 붙이면 이후 빌드가 그 규칙을 물려받는다는 뜻이다.

기존 npm 패키지를 디자인 시스템으로 감싸는 방식은 Enterprise 플랜 전용이라고 같은 항목이 밝혔다. 문서 페이지에도 같은 구분이 있다. React 컴포넌트 라이브러리 기반 시스템은 모든 유료 플랜, npm 래퍼 방식은 Enterprise 전용이다.

디자인 시스템은 어떻게 생겼나

러버블 공식 문서는 디자인 시스템을 "컴포넌트 라이브러리, 스타일 가이드, 설치 방법을 한 번 정의해 워크스페이스의 여러 프로젝트에서 재사용하는 기능"으로 설명한다. 디자인 시스템 자체가 전용 러버블 프로젝트다.

문서가 말하는 구성은 세 가지다.

  1. 컴포넌트. React 컴포넌트 라이브러리
  2. 스키마와 가이드라인. 토큰, 컴포넌트 카탈로그, 제약 조건을 담은 기계가 읽는 스키마와 렌더링된 문서. 러버블이 코드를 만들 때마다 이를 참조한다
  3. 설치 정보. 설정 방법과 필요한 구성

릴리스하면 프로젝트의 .lovable 폴더에 design-system.json, rules/components.md, rules/design-tokens.md, rules/library-guidelines.md가 만들어진다. system.md는 직접 쓰는 파일이고 릴리스 때 덮어쓰지 않는다. 문서는 설계 철학이나 사용 규칙을 여기에 적으라고 안내한다.

이 구조는 앞서 다룬 DESIGN.md와 닮았다. AI에게 주는 디자인 규칙 메모를 파일로 두고, AI가 만들 때마다 읽게 한다는 점이 같다. 러버블은 그것을 서비스 안의 기능으로 묶어 놓은 셈이다.

만드는 순서

문서에 적힌 순서를 줄이면 이렇다.

  1. 프롬프트 박스의 + 메뉴에서 Design → Use a design system → Create design system을 고른다. 이름은 나중에 연결할 때 쓰이니 알아보기 쉽게 짓는다.
  2. 채팅으로 구성한다. 이미 있는 라이브러리를 npm 패키지명이나 공개 Git 저장소 주소로 가져오거나, 목표·기술 스택·원하는 부품·참고 문서(PDF, 마크다운, 스크린샷)를 순서대로 알려 주고 새로 만든다.
  3. Release version을 누른다. 스키마 생성, 문서 렌더링, 버전 증가, 커밋이 이뤄지고 프로젝트에 연결할 수 있게 된다.
  4. 새 프로젝트는 + → Design → Use a design system에서 고른다. 기존 프로젝트는 Project settings → General의 Design system 섹션에서 Attach design system을 누른다.

연결하면 부품이 src/design-system/<슬러그>/로 복사되고, 규칙 파일이 .lovable/rules/libraries/<슬러그>/에 들어간다. 새 버전이 나오면 채팅에 "Update available"이 뜨고, 받아들이면 기존 디자인 시스템 파일이 교체된다. 프로젝트 자체 코드는 바뀌지 않는다고 문서가 적었다.

쓰기 전에 알아 둘 한계

문서가 직접 밝힌 제한 중 디자이너가 알아 둘 것만 추렸다.

  • 프로젝트 하나에 디자인 시스템 하나만 연결된다. 바꾸려면 먼저 떼어 내야 한다.
  • 릴리스하지 않은 초안은 새 프로젝트의 바탕으로 쓸 수 없다.
  • 기존 프로젝트를 디자인 시스템으로 바꿀 수 없다. 새로 만들어야 한다.
  • 연결된 프로젝트의 .lovable 폴더와 복사된 부품은 직접 고치지 않는 것이 좋다. 업데이트하면 고친 부분이 덮어써진다. 영구적인 변경은 디자인 시스템 프로젝트에서 한다.
  • 연결을 끊으면 업데이트와 규칙 적용이 멈추고, 복사된 파일은 일반 코드로 남는다.
  • 공식 지원은 React뿐이다. Vue, Angular, Svelte는 보장되지 않는다.
  • 올린 자료를 읽는 방식은 "best-effort", 곧 최선을 다하는 수준이다. 첫 결과를 직접 검토하라고 문서가 안내한다.

플랜 설명이 어긋나는 부분도 있다. 검색에서 나온 문서 요약에는 "Enterprise 플랜에서 쓸 수 있다"는 표현이 보였지만, 변경 기록(8월 19일)과 문서의 플랜 항목은 React 기반이 모든 유료 플랜이라고 적었다. 결제 전에는 러버블의 요금 안내에서 현재 조건을 확인하자.

같은 시기의 다른 변화

10월 12일 항목은 프로젝트의 Files 탭에서 이미지 위를 직접 그려 표시하거나, 댓글을 핀으로 꽂거나, 지우거나, 배경을 제거할 수 있다고 적었다. 결과는 새 파일로 저장된다. 이미지를 통째로 다시 뽑지 않고 고치는 쪽으로 간다는 점에서, 앞서 다룬 다시 뽑지 말고 고쳐 쓴다와 같은 흐름이다.

이 외에 러버블이 5월에 낸 'Aesthetics' 업데이트가 있다. 러버블의 X 게시물은 타이포그래피, 레이아웃, 색 선호를 요청하고, 짓기 전에 디자인 콘셉트를 미리 볼 수 있으며, 더 대담한 랜딩 페이지·앱·블로그를 만들 수 있다고 소개했다. 날짜(5월 11일)는 2차 매체인 Create With의 보도에서 확인했고, 러버블 쪽 상세 문서는 찾지 못했다. 이 기능과 이번에 사라진 '방향 3안' 단계가 어떻게 이어지는지는 공개된 자료로 확인되지 않았다.

아직 확인되지 않은 것

  • 방향 3안 단계를 없앤 이유. 변경 기록에 설명이 없다.
  • 디자인 시스템을 붙인 빌드와 안 붙인 빌드의 결과 차이를 보여 주는 공개 비교.
  • 디자인 시스템의 크레딧 비용. 문서는 설정 확인 단계가 0크레딧이라고만 밝히고, 업데이트 같은 다른 작업의 비용은 적지 않았다.
  • 변경 기록 뒷부분(이번에 읽지 못한 범위)에 있을 수 있는 관련 항목.

디자이너에게 이것이 의미하는 것

바이브 코더에게는 단순한 소식이다. 모양을 매번 프롬프트로 설득하지 말고, 한 번 정해 둔 규칙을 붙이라는 방향이다. 디자이너에게는 조금 다른 일이다. 버튼·카드 같은 부품과 색·글자 규칙을 AI가 읽을 수 있는 형태로 정리하는 일이 새 업무가 될 수 있다. 이것은 내 추측이다.

피그마 Specs가 시안의 맥락을 마크다운 한 장으로 건네는 구조였다면, 러버블의 디자인 시스템은 코딩 도구 쪽에서 같은 문제를 푸는 방식으로 보인다. 도구는 달라도 '규칙을 글과 파일로 남겨 둔다'는 일은 같다.

그래서 지금은

내 규칙부터 열 줄로 적자. 주 색 하나, 보조 색 하나, 글꼴 둘, 모서리 둥글기, 여백 단위를 먼저 정한다. 러버블을 쓰지 않아도 커서나 클로드 코드에 줄 규칙 메모로 그대로 쓸 수 있다. 작성법은 DESIGN.md 글에 적어 두었다.

첫 프롬프트에서 모양을 비워 두지 말자. 변경 기록에 따르면 색, 글자, 레이아웃을 정하지 않으면 러버블이 되묻는다. 처음부터 "주 색은 이것, 글꼴은 이것"이라고 적어 두면 되묻는 과정을 건너뛸 수 있다.

고친 곳은 규칙 쪽에 반영하자. 문서가 안내하듯 연결된 프로젝트의 복사된 부품을 직접 고치면 업데이트 때 덮어써진다. 마음에 드는 변경은 디자인 시스템 프로젝트에 넣어야 남는다.

쓰임별 AI 디자인 도구는 AI 디자인 툴에 모아 두었다.

정리하면

러버블은 열려 있는 프롬프트에서 방향을 고르게 하던 단계를 없앴고, 부품과 규칙을 한 번 정해 모든 빌드에 물려주는 디자인 시스템을 모든 유료 플랜의 기능으로 내놓았다. 그것이 화면이 덜 비슷해지게 만드는지는 아직 확인된 바 없다. 확실한 것은 모양을 정하는 일이 프롬프트 한 줄에서 규칙 파일로 옮겨 가고 있다는 점이다.
